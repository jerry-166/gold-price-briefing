## 金价早报调度器再次缺跑（9/6-9/7缺失、9/8延迟30分钟）

### 现象
- 2026-09-08 09:30 早报任务才被触发执行（定时 9:00，延迟约 30 分钟），而非准点触发。
- 检查 daily/ 目录与 git 历史：2026-09-06（周日）与 2026-09-07（周一）早报**完全缺失**（最近一次成功为 9/5 补跑，commit 9b3d5f9/db4e9d1）。同日（9/7）的 PM/晚间巡检日志正常存在（git 947a27b/6397031），说明只有「早报」这一条定时缺失，其他定时任务正常。
- BUG-002（9/5 记录 9/1-9/4 缺失）之后，缺跑问题仍在复发：9/5 补跑成功 → 9/6、9/7 又连续两天缺跑 → 9/8 延迟 30 分钟才触发。

### 根因分析
- 与 BUG-001/BUG-002 同源：**宿主侧调度器对「金价早报」这一条 9:00 定时触发持续不可靠**，表现为准点不触发、延迟或整日缺失。巡检类任务（PM/晚间）触发正常，指向该条定时器本身（而非宿主整体）存在投递问题。
- 时间线：8/27 延迟至 10:25/10:41 → 8/30 延迟至 23:55 → 9/1-9/4 全缺、9/5 延迟至 16:20 → 9/6-9/7 全缺 → 9/8 延迟至 09:30。规律明显：缺失/延迟以「天」为单位随机发生，无自愈机制。
- 早报流程仍缺少「距上次成功早报超过 1 个交易日即告警」的兜底；本次 9/8 生成时，图表窗口需手工补 9/6（沿用 9/5 收盘）与 9/7（真实收盘 4406）两个点，数据断档的处理成本持续累积。

### 修复过程
- 本次触发：无同日产物 → 正常执行全流程。9/7（周一）为真实交易日且有公开收盘价（现货金收 4406、上金所昨结 949.6），已在 chart/数值中如实回填并标注来源，非伪造。
- 9/6（周日休市）沿用 9/5 收盘值并在 chart source 中标注「周末沿用值」。
- 缺失的 9/6-9/7 早报 JSON 不做回溯补生成（沿用 BUG-002 结论：不伪造历史数据）。
- 建议（待宿主侧落实）：① 单独核查「金价早报」这条 9:00 定时器的投递记录，为何与巡检任务不同；② 增加跨日未成功的宿主侧主动提醒；③ 早报头部检测到与上次成功记录间隔 >1 个交易日时，在输出与邮件顶部显著提示数据缺口。

### 经验教训
- 调度类缺陷必须按「单条定时器」粒度排查——同一宿主下其他任务正常不代表目标任务正常，缺跑证据要细化到具体任务级。
- **「延迟」与「缺跑」是两种不同严重级的失效形态，不可合并同类项**：延迟只影响快照时点，缺跑会造成数据永久断档。此前十日只有延迟，容易让人低估风险、误判为「有界可接受」；一旦出现缺跑，必须立即升级处置优先级并补上缺失检测兜底。
- 早报内容里的行情时间戳/图表断点，宁可如实标注「沿用」「估算」也不伪造精确收盘，保持数据可信度。
- 每次复发都在 automation memory + buglog 留痕（BUG-001→003 已形成时间线），为宿主侧定位提供完整证据链。
- 延迟触发时，早报的 `updateTime` 固定写 09:00（定时口径），真实触发时间记入 logs 的 `timestamp` 字段，避免污染站点展示口径。
