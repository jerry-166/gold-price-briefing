## 提交前自检脚本的 ASCII 引号扫描产生大量假阳性

### 现象
- 生成 `daily/2026-09-24.json` 后执行提交前五合一自检，其中「无 ASCII 直双引号出现在中文正文中」这一项报告 **128 处命中**。
- 但同一个 JSON 文件 `json.load` 解析**完全成功**，说明不存在 BUG-009 那类「未转义引号导致解析失败」的问题——逻辑上这两件事不可能同时成立（真有 128 个未转义引号，解析必然早就报错）。
- 结论：这 128 处全部是**假阳性**（false positive），属自检脚本自身的缺陷，而非产物缺陷。

### 根因分析
- BUG-009 定下的规则是「手写 JSON 内引中文一律用 `“ ”` / `『 』`，禁 ASCII 直引号」，本意是**约束中文正文**（`note`、`detail`、`explain` 等自由文本字段）。
- 但自检脚本把这条规则实现成了「对整份 JSON **文件原文**做正则扫描」，正则为 `.{12}\".{12}`——它匹配的是「任意 12 字符 + 一个 ASCII 双引号 + 任意 12 字符」。
- 而**合法 JSON 的语法结构本身就充满 ASCII 双引号**：每个键名的开引号、每个字符串值的开引号都是。一份 30 个价位、5 条新闻、13 个 dataSources 的早报 JSON 含数百个结构引号，因此必然产生大量命中。
- 更深一层的缺陷：脚本**无法区分「结构引号」与「正文引号」**。`{"note": "含引号\"的文本"}` 里，键名旁的结构引号与正文里真正未转义的引号，在这个正则下长得一模一样。
- 触发条件：只要跑这个脚本就必然触发，与产物质量无关——这是一个「每次都亮红灯」的无效检查，长期看会训练出「忽略该项告警」的坏习惯，反而比没有检查更危险。

### 修复过程
1. 本次通过两个独立证据判定为假阳性并**未阻断流程**：① `json.load` 解析成功，与「存在 128 个未转义引号」在逻辑上互斥；② 128 这个数量级与产物规模（约 30 项带引号字段）同量级，符合「结构引号被全部误报」的特征。
2. **正确做法（待落实，本 bug 维持 open）**：引号检查必须**作用在解析后的字符串值上，而不是文件原文上**。即先 `json.load`，再递归遍历所有字符串字段，对每个值做「是否含 `"`」的判断——这样结构引号天然被排除在外。参考实现：
   ```python
   def walk(o, path=''):
       if isinstance(o, str):
           if '"' in o:
               print('ASCII quote in', path)
       elif isinstance(o, dict):
           for k, v in o.items(): walk(v, f'{path}.{k}')
       elif isinstance(o, list):
           for i, v in enumerate(o): walk(v, f'{path}[{i}]')
   walk(d)
   ```
3. 由于本次未实际修改脚本文件（自检是以 inline `python -c` 方式临时执行的），本条记录的是**方法缺陷**而非代码缺陷；下次执行前应把上述正确实现固化进自检流程或写入 skill。

### 经验教训
- **校验规则的作用域必须与其约束对象一致**：针对「字段内容」的规则，就必须在「字段内容」这一层校验，不能图省事退化成对文件原文做正则。原文层面的扫描会被 JSON 语法本身污染。
- **一个「每次运行都报警且报警无意义」的检查，比没有检查更有害**——它会训练执行者忽略告警，等到真问题时被一并忽略。凡是高频假阳性的检查项，应优先修脚本而不是绕过去。
- **交叉验证能救回被误判的流程**：本次靠「`json.load` 成功」这一独立信号反证了引号扫描的结果不可信。当两个校验项结论互斥时，不要急着改产物，先判断哪个校验本身有问题。
- BUG-009（转义导致语法错误）、BUG-010（内容正确性）、本条（校验器缺陷）构成提交前自检的三个不同层次：**语法层 / 内容层 / 校验器自身可信度**。前两层已固化，第三层此前从未被审视过——校验脚本本身也是需要被验证的代码。
