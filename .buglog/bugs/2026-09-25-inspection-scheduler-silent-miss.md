## 巡检定时任务连续七日缺跑（9/18-9/24），且「晚间巡检」提前约12.5小时触发

### 现象
在 2026-09-25 早报执行时顺带核查 `logs/` 目录，发现两条此前未被记录的问题：

1. **巡检任务连续七日缺跑（9/18-9/24）**。`logs/` 中最后一条巡检日志是 `2026-09-17-inspection_pm.json` 与 `2026-09-17-inspection_noon.json`；此后 9/18（周五）、9/19（周六）、9/20（周日）、9/21（周一）、9/22（周二）、9/23（周三）、9/24（周四）**七天无任何 inspection 日志**（既无 `inspection_noon` 也无 `inspection_pm`），`logs/manifest.json` 亦无对应条目。期间早报链路是「延迟 + 9/23 缺跑 + 9/24 补跑」，巡检链路则是**连续七天完全静默**。
2. **「晚间巡检」在 9/25 反向提前约 12.5 小时触发，且类型标记存疑**。`logs/2026-09-25-inspection_pm.json` 的 `timestamp` 为 `09:31 CST`，但其自身 `summary` 写的是「**晚间巡检(22:00定时，09:31提前触发)**」，同时 `type` 字段为 `inspection_pm`、git 提交信息为「日志：巡检 2026-09-25 晚间」。也就是说：一条标称 22:00 的任务在**当天 09:31** 就跑掉了，比其标称时点早了约 12.5 小时——这是与 BUG-003 的「延迟」方向**相反**的失效形态。

### 根因分析
- 与 BUG-002 / BUG-003 同源，指向**宿主侧调度器对本站多条定时任务的投递不可靠**。早报链路此前已确认为「延迟 + 静默缺跑」，本次证据表明**巡检链路（标称 14:00 / 22:00）的失效程度可能更重**：早报至少多数日子还有产出，巡检是连续七天零产出后突然反向提前触发。
- 「提前 12.5 小时触发」比「延迟」更难用单纯的队列积压解释。可能的机制有三：① 调度器把「上一次错过的 22:00 触发」在本次会话中被补投，但因无日历校验而与 09:31 的实际时点拼在一起，并被任务脚本按「提前触发」自我描述；② 宿主侧时区/时点解析错误，把 22:00 理解成另一个时区或另一日；③ 巡检任务脚本自身在描述触发时点时判断有误（把 09:31 与 22:00 的差异归因为「提前」而非「跨日补投」）。**在拿到宿主侧投递记录前无法定论**，但无论哪种机制，结果都是「产出时点与标称时点严重脱节，且日志自我描述与实际不符」。
- 与 BUG-005（午后巡检误标为 `inspection_pm`）存在关联风险：本次 `type=inspection_pm` 而 summary 自称「晚间巡检」，二者的语义边界再次出现混淆，说明**巡检任务的「类型标签」与「标称时点」两个字段长期依赖任务脚本自觉填写，没有任何一致性校验**。
- 后果：巡检的职责是在盘中振幅越阈值或出现突发消息时提前预警（如 9/17 的 `status: partial`）。连续七日静默意味着 9/18-9/24 期间（正好覆盖金价从 4377 一路跌破 4300、单日暴跌 1.65% 的剧烈波动段）**完全没有任何盘中预警能力**，而这些恰恰是巡检最该发挥作用的时段。

### 修复过程
- 本次仅完成**发现与留痕**，未修改任务脚本（巡检脚本不在本次早报执行的职责范围内）。
- 已记录后续待办：① 尽快核查宿主侧 14:00 / 22:00 两条定时任务的投递记录，确认 9/18-9/24 是完全未投递还是投递后执行失败；② 在巡检任务开头加入「距上次成功巡检是否超过 1 个交易日」的前置检查，超限则在日志 `summary` 中显著标注缺口（与 BUG-003 建议 ④ 对称）；③ 为巡检日志增加「标称时点 vs 实际时点」的机器校验，当偏差绝对值超过阈值（如 60 分钟）时在 `summary` 中打 `schedule_anomaly` 标记，避免「提前 12.5 小时」被轻描淡写为「提前触发」；④ 统一 `type` 字段的取值口径（`inspection_noon` / `inspection_pm` 与「午后/晚间」的对应关系需写死在脚本里，不靠模型临场判断）。

### 经验教训
- **排查调度异常时必须同时扫描「产出物目录」而不是只看单条任务**。本次若不是顺带 `ls logs/`，七日巡检缺跑会继续静默。建议把「早报 + 巡检」两条链路的历史产出纳入同一个体检脚本。
- **「提前触发」是独立于「延迟」的第三种失效形态**，且因任务脚本倾向于把它自我描述为「提前触发」而显得无害，容易被忽略。它的真实含义可能是「跨日补投」「时区解析错误」或「日志描述失真」——三者都需要查证，不能接受任务脚本的自我解释。
- 巡检的日志 `type` / 标称时点必须由脚本常量决定，**不得由模型在运行时判断填写**；凡依赖模型临场判断的元数据字段，都应加一致性校验。
- 与 BUG-003 同源，**根本修复点在宿主侧调度器**；任务侧只能做「缺口检测 + 显著标注」的被动兜底。
