## 自动化会话被中断后半成品残留：daily JSON 已推送但 logs 缺失、邮件未发且无任何中断标注

### 现象
2026-10-06 的金价早报（automation-1784188098041）出现了「同一日跑了两段」的形态：

- **第一段（约 10:30-10:49）**：完成步骤 1-4——`daily/2026-10-06.json`（10:48 写入）、`manifest.json` 追加、`git commit 24afd0d` 并推送到远端（10:49:18）。数据完整、自检可通过。
- **中断点（11:46）**：`logs/2026-10-06-morning_briefing.json` **不存在**，`logs/manifest.json` 最新一条仍是 10/05 的 `inspection_pm`；邮件同样未发出。同时本机 `~/.workbuddy/` 下的 `.skill-list-cache.json`、`.legacy-localstorage-migration.done`、`.playwright-driver-node-reuse.done` 时间戳**全部为 11:46**。
- **第二段（11:46 触发，本会话）**：复查发现上述残留状态。

即：**站点上已经"看起来完成了今日早报"，但运行日志与邮箱投递都缺位，且没有任何地方记录"这次运行是被中断的"**。若本会话只是简单地重跑全流程，还会造成二次抓数、二次提交与重复发信。

### 根因分析
1. **中断来源是宿主/应用侧，不是任务逻辑**：11:46 的 `.legacy-localstorage-migration.done`（旧版 localStorage 迁移完成标记）与 `.skill-list-cache.json` 刷新，说明应用在 11:46 前后完成了一次**版本更新并重启**。运行中的自动化会话被随进程终止，步骤 5-7 直接丢失。
2. **流程本身没有「断点续跑」与「进行中留痕」机制**：
   - 步骤 1-4 是**改站点可见产物**的动作，先落盘先推送；步骤 5-7 是**留痕与投递**动作，后置。一旦在中途被杀，产物就停在"半成品 + 无记录"的状态，且因为 daily JSON 与 manifest 都已提交，重跑时**无法从产物本身判断今日早报是否真的完成**。
   - 没有 `status: in_progress` 的中间态日志，因此**触发时刻、已完成到第几步、失败原因全部丢失**——连带 BUG-003 的延迟指标也失去精确值（只能回溯估算为约 90 分钟）。
3. **重跑缺少幂等判断**：任务提示词要求"生成 daily/YYYY-MM-DD.json → 追加 manifest → git 提交 → 发邮件"，未要求先检查当日产物是否已存在。本会话之所以没有重复劳动，是**人工介入判断**（先读 git log 与文件 mtime、比对 commit）的结果，不是流程自带的保护。
4. **两个下游后果被放大**：① 邮件未发（叠加 BUG-006 的双通道不可用，形成"既不重试、也无兜底"）；② 「站点已更新、日志无记录」会让 `logs/` 四维体检把它误判为「当日早报缺失」，或在补记时误记成一次成功的完整运行。

### 修复过程（本次处置）
- **先取证再动作**：读取 `git log`（发现 `24afd0d 每日早报 2026-10-06` 已在 10:49 提交）、比对 `daily/2026-10-06.json` 的 mtime（10:48）与 `logs/` 目录（无 10-06 文件）、核查 `logs/manifest.json` 头部（仍为 10/05），确认「产物已推送但留痕缺失」。
- **确认不重复生成**：对已发布的 `daily/2026-10-06.json` 补做完整提交前自检（解析 + 结构断言、labels/values 各 30 且唯一、events 索引与日期逐条比对、与 10/05 的图表滚动平移比对、全部 ¥/克 价位复算、引号检查、`trend.advice` 字数），十项全部通过 → **判定无需回填、无需重发数据**，仅补齐缺失步骤。
- **补齐留痕**：写入 `logs/2026-10-06-morning_briefing.json`（`status: partial`、`email_sent: false`、`git_pushed: true`，并在 `timestamp` 与 `notes` 中显式标注「触发时刻为回溯估算」与中断原因），并在 `logs/manifest.json` 头部插入同日记录。
- **邮件步骤如实记失败**：不写"已发送"，改为记录双通道不可用（BUG-006）并明示需人工补发。

### 经验教训
- **产物先落盘 ≠ 任务已完成**。凡是「改站点可见产物」与「留痕/投递」分属不同步骤的自动化，都必须有一个**中间态标记**（最小日志 / 状态文件），否则中断后的真实进度不可知。
- **触发时刻应在会话开始的第一时间落盘**（已作为 BUG-003 建议 ⑦ 提出）。本次 BUG-003 的延迟值只能给「约 90 分钟」的估算，正是缺了这一条的直接代价。
- **重跑必须先做「当日产物是否已存在」的幂等检查**：读 `daily/<今日>.json` 是否存在、`logs/manifest.json` 头部是否已有今日记录、`git log` 当日是否已有早报提交。三者比对即可判断该从哪一步续跑，避免二次抓数与重复发信（与 BUG-001 的"重复触发"同源风险）。
- **「站点已更新但日志缺失」是一个必须被识别的合法状态**，体检与补记时不得直接判为「当日早报失败」或「完整成功」，应记 `partial` 并写明由哪一段补齐。
- 宿主侧建议：自动化被应用更新中断时，若任务有落盘痕迹，应在重启后**以「续跑 + 标注中断」的方式恢复**，而不是静默丢弃该次运行。
