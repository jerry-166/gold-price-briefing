# BUG-019 第三个百分号家族：JSON 正文里的裸 % 打断 % 格式化

## 现象

2026-11-04 早报运行 `scripts/build_2026_11_04.py`，连续三次失败，每次只暴露一处、改完再跑又冒出新的一处：

```
ValueError: unsupported format character '?' (0xff0c) at index 298   # 「+0.98%」后跟中文逗号
ValueError: unsupported format character '?' (0xff09) at index 174   # 「跌 0.49%」后跟中文右括号
ValueError: unsupported format character '?' (0xff08) at index 134   # 「-0.42%」后跟中文左括号
```

三次都发生在 `prices[].source` 这类**长中文正文 + 行尾 `% (a, b)` 格式化**的写法里：正文本身写的是给人看的「+0.98%」「跌 0.49%」单个百分号，而该行又用 `%` 运算符做了格式化，于是 Python 把 `%` 后面的中文字符当成非法转换符。

## 根因

与 BUG-017、BUG-018 同一家族，但位置上升了一层：

- BUG-017：**不该转义却转义了**——字面量行写了 `%%`，产物里留下非法的 `width:100%%`。
- BUG-018：**该转义没转义**——往已格式化的行里插裸 `%`，抛 `TypeError`。
- **BUG-019：转义正确性依赖「这一行到底有没有被格式化」这个隐性前提，而这个前提在长中文串里根本看不出来**。更糟的是其中两处是**多余的格式化**——那两行根本没有 `%s` 占位符，`"…0.49%。" % RATE` 纯属多余，白白引入了转义风险。

## 修复

1. 三处裸 `%` 改为 `%%`（`+0.98%%`／`+0.86%%`／`+0.82%%`）。
2. 对**没有占位符的行**批量剥离多余的 `% XXX` 运算符（用脚本按 `"\s*%\s*[A-Za-z_]…,` 结尾 + 正则检测 `%(s|d|\.\d+f)` 是否真的存在来判定），剥离 1 处。
3. 改完 `check_briefing.py` 0 error。

## 经验教训

- **长中文正文一律不要用 `%` 运算符格式化**。本次之后约定：正文类字段（`source`／`note`／`explain`／`trigger`）统一改用 f-string 或字符串拼接，`%` 只留给纯数值模板。f-string 里 `%` 是普通字符，从根上不会踩这个坑。
- **失败的粒度很坑**：Python 只报第一个非法转换符，一个文件里有多少处裸 `%` 就要跑多少轮，一次运行看不出全貌。所以要么一次改到位（改写法），要么在生成前 grep 一遍 `"[^"]*%[^sdf%]` 之类的模式。
- 判定标准沉淀：`%` 运算符只应在「该字符串确实需要插值」时使用；多余的格式化不是无害的，它会把普通文本变成模板。
